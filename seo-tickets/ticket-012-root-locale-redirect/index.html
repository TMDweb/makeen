Ticket #012 - Root URL Locale Redirect & x-default Hreflang

Project:asasmakeen.com
Priority:Medium
Date:June 10, 2026
Assignee:Abdo (dev, Makeen)

ملخص المهمة

الصفحة الرئيسية asasmakeen.com/ تعمل بنظام كشف اللغة: تحوّل الزائر تحويل 302 إلى /ar أو /en حسب لغة المتصفح. هذا النمط بحد ذاته صحيح ومدعوم من Google، لكن وسوم hreflang الحالية تتعارض معه: x-default يشير إلى /ar بينما يجب أن يشير إلى الجذر / نفسه (صفحة الكشف).

المطلوب: تغيير قيمة x-default في الصفحتين الرئيسيتين (عربي وإنجليزي) لتشير إلى https://asasmakeen.com/، مع إبقاء التحويل 302 كما هو (لا يُغيَّر إلى 301). وهناك نقطة قرار للعميل: الزائر بدون لغة محددة يُحوَّل حالياً إلى الإنجليزية، والأنسب لسوق سعودي أن يكون الافتراضي العربية.

The root URL https://asasmakeen.com/ is a locale-detection redirect: it 302s to /ar or /en based on the browser's Accept-Language header. This pattern (302 + language detection at the root) is legitimate and supported by Google, and the 302 is deliberately correct here - it must not be "fixed" into a 301.

The actual defect is an hreflang contradiction: both homepages declare x-default = /ar, while the root redirect sends crawlers and header-less visitors to /en. The fix is to point x-default at the root / itself, so Google understands the root is the international default (the detector page) and consolidates the homepage signals correctly.

🔎 Current Behavior (verified 2026-06-10)

Request to https://asasmakeen.com/ Response
Accept-Language: ar-SA,ar 302 → /ar
Accept-Language: en-US,en 302 → /en
No Accept-Language header (most bots, incl. Googlebot) 302 → /en

Meanwhile both /ar and /en declare in their <head>:

🖥️ Current hreflang on /ar and /en
<link rel="alternate" hreflang="ar" href="https://asasmakeen.com/ar">
<link rel="alternate" hreflang="en" href="https://asasmakeen.com/en">
<link rel="alternate" hreflang="x-default" href="https://asasmakeen.com/ar">

Why this is a problem: the markup tells Google "the default version for unmatched languages is /ar", but the server behavior sends every unmatched visitor (and Googlebot itself, which crawls without Arabic headers) to /en. Conflicting signals weaken the hreflang cluster, and the root - the URL that earns nearly all external backlinks - is left out of the cluster entirely.

🛠️ The Fix

1. Point x-default at the root (required)

On both homepage language versions (/ar and /en), change the x-default alternate to the bare root. This is Google's documented pattern for homepages with automatic locale redirection: x-default should reference the detector/selector URL, and it is fine that this URL itself redirects.

🖥️ Target hreflang on /ar and /en
<link rel="alternate" hreflang="ar" href="https://asasmakeen.com/ar">
<link rel="alternate" hreflang="en" href="https://asasmakeen.com/en">
<link rel="alternate" hreflang="x-default" href="https://asasmakeen.com/">

This change applies to the homepage cluster only. Inner pages (blogs, projects) keep their current per-page x-default pointing at the Arabic version - do not touch those.

2. Keep the 302 (do not change)

The root redirect stays a 302. A 301 would tell Google the root is permanently gone and the detection is not permanent - it varies per visitor. This is the one place on the site where a 302 is the correct status code.

3. Default fallback language (client decision)

Visitors with no language preference currently fall back to English. For a Saudi-market business whose primary audience and content are Arabic, the more natural fallback is /ar. This is a one-line change in the detection logic but it is a business decision - confirm with Makeen before changing. It does not block items 1-2.

✅ Verify

Pass = the x-default line on both homepages points to the bare root, and the root still answers 302.

$ curl -s https://asasmakeen.com/ar | grep -o '<link[^>]*x-default[^>]*>'

$ curl -s https://asasmakeen.com/en | grep -o '<link[^>]*x-default[^>]*>'

$ curl -sI -H "Accept-Language: en" https://asasmakeen.com/ | grep -i -e '^HTTP' -e '^location'
