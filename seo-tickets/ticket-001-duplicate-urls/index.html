Project: asasmakeen.com

ملخص المشكلة

كل صفحة على موقع مكين تنتج حالياً 4 روابط مختلفة بدلاً من 2 فقط. السبب هو أن النظام يخلط بين الروابط العربية والإنجليزية، فيظهر الرابط العربي في المسار الإنجليزي والعكس.

هذا يسبب مشكلة كبيرة في محركات البحث لأنها تتعامل مع كل رابط كأنه صفحة مستقلة، مما يضعف ترتيب الموقع بشكل ملحوظ.

المطلوب: عند استخدام رابط بلغة خاطئة، يتم تحويل المستخدم تلقائياً (301 redirect) إلى الرابط الصحيح بدلاً من عرض نفس المحتوى على أكثر من رابط.

Every page on the website currently generates 4 different URL versions when it should only have 2 (one Arabic, one English). The system is creating extra versions by mixing up Arabic and English slugs across both language paths. This is a critical SEO issue - search engines see these as duplicate pages, which splits the site's ranking power across multiple copies of the same content.

🔍 What's Happening - Step by Step

When a new page is created (for example, a property listing or a blog post), the system generates a URL slug in both Arabic and English. That part is fine - we need both languages.

The problem is: every slug is made accessible under every language path. So instead of the Arabic slug only working on the Arabic version of the site, it also works on the English version - and vice versa.

🧩 The Simple Rule

❌ Current behavior (wrong)
1. Arabic page + Arabic slug /ar/.../‫شقق-حي-الروابي‬
2. Arabic page + English slug /ar/.../al-rawabi-apartments
3. English page + English slug /en/.../al-rawabi-apartments
4. English page + Arabic slug /en/.../‫شقق-حي-الروابي‬
✅ Expected behavior (correct)
1. Arabic page + Arabic slug /ar/.../‫شقق-حي-الروابي‬
2. English page + English slug /en/.../al-rawabi-apartments
That's it. Only 2 versions.
💡
The rule is simple: The slug language must match the page language. Arabic pages get Arabic slugs only. English pages get English slugs only. A mismatched slug (e.g., English slug on an Arabic page) should not exist at all - it should not resolve, redirect, or return any content.

🛠 What Needs to Be Done

1
Find where slugs are resolved to pages

In the routing layer (backend or CMS config), find the code that takes a URL like /ar/u/pu/3/38/some-slug and looks up the page. This is where the bug lives - it currently accepts any slug regardless of language.

2
Add a language check on slug resolution

When the URL starts with /ar/, only resolve the page if the slug is the Arabic version. When it starts with /en/, only resolve if the slug is the English version. If the slug language doesn't match the path language, don't show the page.

3
Redirect mismatched slugs (don't just 404)

When someone visits /ar/.../makeen-51-east-riyadh-compounds (English slug on Arabic path), redirect them with a 301 redirect to the correct version: /en/.../makeen-51-east-riyadh-compounds. This preserves any SEO value those wrong URLs have already accumulated.

4
Ensure each page stores one slug per language

In the database, each page entry should have exactly one Arabic slug and one English slug. If any page has multiple slugs in the same language (like Makeen 68 above), clean those up so only one remains.

⚠️
Important: Do NOT simply delete the wrong URLs or return 404 errors. Google has already indexed many of these. They need 301 redirects to the correct version so we don't lose any ranking value. A 301 redirect tells Google: "this old URL has permanently moved to this new URL - transfer all ranking power to the new one."

💻 Logic Reference

Below is simplified pseudocode showing the expected behavior. This is not meant to be copy-pasted - adapt it to our framework and routing system.

📄 Pseudocode - Slug Resolution Logic 
// When a request comes in:
// URL example: /ar/u/pu/3/38/makeen-51-east-riyadh-compounds

pathLang = extract language from URL path    // "ar"
slug    = extract slug from URL path          // "makeen-51-east-riyadh-compounds"
pageId  = extract page ID from URL path        // "38"

// Look up the page in the database
page = database.findById(pageId)

// Check: does the slug match the language in the URL?
if pathLang == "ar" AND slug == page.arabicSlug:
    → Serve the Arabic version of the page ✅

elif pathLang == "en" AND slug == page.englishSlug:
    → Serve the English version of the page ✅

elif pathLang == "ar" AND slug == page.englishSlug:
    → Wrong! English slug used on Arabic path
    → 301 Redirect to: /en/u/pu/3/{pageId}/{page.englishSlug}

elif pathLang == "en" AND slug == page.arabicSlug:
    → Wrong! Arabic slug used on English path
    → 301 Redirect to: /ar/u/pu/3/{pageId}/{page.arabicSlug}

else:
    → Slug doesn't match any known version
    → Return 404

✅ How to Know This Is Done

  • Each page has exactly 2 working URLs: one under /ar/ with an Arabic slug, one under /en/ with an English slug.
    Test with any property page - e.g., Makeen 51 (ID: 38). Only 2 URLs should return a 200 status.
  • Visiting an Arabic page with an English slug (e.g., /ar/.../makeen-51-east-riyadh-compounds) returns a 301 redirect to the correct English page.
    Use curl -I [url] or browser dev tools Network tab to confirm 301 status and correct Location header.
  • Visiting an English page with an Arabic slug (e.g., /en/.../مكين-51-مجمعات-شرق-الرياض) returns a 301 redirect to the correct Arabic page.
    Same verification as above - check for 301 and correct redirect target.
  • Pages with multiple slugs in the same language (like Makeen 68) are cleaned up so only one slug remains per language.
    The extra slug should 301 redirect to the primary slug.
  • This fix applies to all content types: property pages (/u/pu/), blog posts (/blogs/), and any other page type.
    Test at least one URL from each content type.
  • No existing working pages are broken by this change.
    The 2 correct URLs (Arabic page + Arabic slug, English page + English slug) must continue to work exactly as before.
